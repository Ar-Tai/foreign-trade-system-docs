# 多租户与数据隔离设计

## 身份到数据的链路

认证模块验证用户身份后，从服务端的成员关系选择当前租户。切换租户必须重新确认成员关系与权限。业务表采用 `tenant_id` 与资源 ID 的组合唯一约束；外键或应用层等效约束必须保证关联对象属于同租户。

对单租户部署，也保留数据归属和权限范围，不因只有一个租户就删除访问控制。

## 隔离范围

1. 所有列表、详情、搜索、导出及聚合查询包含租户和岗位数据范围。
2. 缓存键含租户与必要的权限范围，权限变更后相关缓存失效。
3. 附件对象路径含不公开的归属信息，下载仍检查元数据授权，不凭路径前缀授权。
4. 后台任务携带经服务端构建的租户、主体、资源和权限快照；敏感导出交付时再检查当前权限。
5. 第三方连接绑定唯一租户；回调中的 tenant 字段不具有授权效力。
6. 指标、追踪和故障日志避免记录明文客户资料、银行信息与完整请求正文。

## 隔离实现选择

共享数据库加租户字段是初始设计假设；高隔离场景可评估独立 Schema 或独立数据库。若使用数据库行级策略，它只是第二道防线，不能替代应用级资源授权。迁移、维护脚本及备份导出同样必须限制作用域。

## 管理员访问

平台运维默认无业务内容访问权。故障协助采用限时授权、具体租户、指定目的和全量审计。禁止在生产中使用全能共享账号，禁止为了调试关闭全局租户过滤。

## 必测攻击面

修改资源 ID、传入别人的附件编号、借用导出任务 ID、复用另一租户幂等键、访问跨租户缓存、搜索聚合泄露数量、Webhook 外部映射串联。所有拒绝必须避免在错误文本中暴露另一方的公司名或订单金额。
